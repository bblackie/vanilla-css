Plain CSS version

Three ways to style the same site

This site, the W3.CSS site and the Pico CSS site are the same Flask application with the same database and the same SQL. Only the templates and the stylesheets differ. Here is what that experiment actually showed.

The question

Every website needs CSS. The choice is not whether to style a site but who writes the styles: you, or a library somebody else wrote. That is the only real decision, and it has consequences beyond how the page looks.

To test it properly we built the same site three times. Identical app.py, identical schema.sql, identical seed.py, identical SQL query. The Python files are byte-for-byte the same in all three folders. Everything you see below comes from changing nothing but the presentation layer.

If the backend never changed, then every difference between the three sites is a difference in how you write HTML and CSS — not in what the site can do.

1. Plain CSS — write it yourself

No library. One stylesheet, written by hand, loaded by base.html. This is the version you are reading now.

The advantages

  • Nothing to load. No CDN request, no dependency, no version to keep up to date. The site works offline and in a locked-down school network.
  • The HTML stays readable. Seven class names across the whole listing page. You can look at the markup and see the content, not a wall of styling instructions.
  • Total control. Nothing is fighting you. There is no library rule to override, no !important to out-rank, no surprise defaults. If the page looks wrong, the reason is in your file.
  • You actually learn CSS. This matters more than it sounds. Flexbox, Grid, the cascade and specificity are transferable skills. W3.CSS class names are not — they are worth nothing the moment you use a different library.
  • The site looks like yours. A framework's defaults are recognisable. Hand-written CSS is the only way to look like nobody else.

The cost

Speed. This version needed by far the most CSS, and every responsive breakpoint is a media query you write and debug yourself. If you do not already know Flexbox and Grid, you will spend your time fighting layout instead of building features.

2. W3.CSS — a class for everything

A utility library. You add class names like w3-card-4, w3-theme and w3-col m4 to your HTML, and the library supplies the rules. It defines around 360 classes in about 23 KB.

The advantages

  • Almost no CSS to write. This was the clear winner on volume. The gallery page — a fully responsive 12-column tile grid — needed zero lines of layout CSS from us.
  • The 12-column grid is genuinely excellent. s6 m4 l3 means two tiles per row on a phone, three on a tablet, four on a laptop. Read them as fractions of twelve. No media queries, no thinking.
  • Themes are one line. Swapping the theme stylesheet recolours the entire site, provided you use w3-theme rather than w3-green anywhere you need the brand colour.
  • Fast to build and hard to make ugly. The spacing and colour system is consistent by default. For a school project on a deadline this is a real advantage, not a small one.
  • The documentation is aimed at beginners. Every class has an example you can copy.

The cost

The HTML gets noisy — 29 class names on the listing page against seven here. And <div class="w3-card-4 w3-white"> tells a screen reader nothing about what the box is. Underneath, the column system uses floats rather than Grid, which is why the gallery needs a w3-clear after it and why the right-hand nav links have to be written back-to-front in the source.

3. Pico CSS — style the HTML you already have

The opposite idea. Pico styles plain HTML elements directly and gives you around 149 CSS variables to customise them. An <article> is a card. A <nav> is a nav bar. A <table> is already striped.

The advantages

  • The cleanest HTML of the three. Six class names on the listing page. Semantic elements do the work, so the markup describes the content rather than its appearance.
  • Accessibility comes along for the ride. Using <article>, <figure> and <nav> because they look right also means screen readers and search engines understand the page.
  • Dark mode, free. Delete one attribute and the site follows the visitor's operating system. Every variable has a light and a dark value. Neither of the other two options gives you this.
  • Variables beat classes for customising. Writing background: var(--pico-primary-background) means your own CSS recolours with the theme automatically. You extend the library instead of fighting it.
  • Forms are excellent out of the box — worth knowing if your project has a login or a contact page.

The cost

It is the largest download of the three at about 80 KB, and it barely does layout. Pico's own .grid only makes equal columns on a single row, so both the listing and the gallery needed hand-written CSS Grid anyway. Pico is a content and component library, not a layout one — which means you still need to know Grid before it helps you.

How to choose

There is no correct answer, and an examiner is not looking for one. They are looking for a decision you can justify. Three honest recommendations:

Pick plain CSS if…

you want to learn CSS properly, your design is unusual, or you need the site to work with no internet connection. Budget more time.

Pick W3.CSS if…

your site is mostly grids and cards, you are short on time, and you would rather spend it on the Python and the database.

Pick Pico if…

you care about clean, accessible markup, you want dark mode, and you are already comfortable enough with Grid to do your own layout.

Whichever you choose, write down why before you start. That sentence is worth more marks than the choice itself.
